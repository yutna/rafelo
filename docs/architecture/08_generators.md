# 08 — Generators

Engines and pages are created and reshaped by generators in
`engines/core/lib/generators/rafelo/`. Generators are part of the architecture:
if they produce code that breaks a rule, every new module starts broken. So
they derive what they can from the same sources the app uses, and CI runs them
for real.

```sh
bin/rails generate rafelo:module billing --icon receipt             # product module (GEN-01)
bin/rails generate rafelo:domain customers                          # domain engine (GEN-05)
bin/rails generate rafelo:page billing invoices --actions=index,show,new,edit   # (GEN-02)
bin/rails generate rafelo:rename_module billing invoicing           # (GEN-06)
bin/rails generate rafelo:move_page billing payments refunds        # move resource "refunds" (GEN-06)
```

Every generator that names an engine (`rafelo:module`, `rafelo:domain`,
`rafelo:rename_module`) refuses a name that is already taken, that collides with
an npm scope used in `package.json`, that is reserved (`core`,
`design_system`, `app`, `engines`), that starts with the reserved
`example_` prefix (GEN-08), or that the registry's boot validation would
refuse (ARCH-06): a locale-shaped key, an app route name or first path
segment, or a kernel error-code prefix. No generator edits the application's
`config/routes.rb` or the `Gemfile`.

## Rules

### GEN-01 — `rafelo:module` creates a product module wired through the registry (MUST · ADR-03, ADR-04)

The module generator creates `engines/<module>/` with:

```text
engines/billing/
  acme_billing.gemspec
  lib/acme/billing/engine.rb      # isolate_namespace Acme::Billing; adds db/migrate to the app's migration paths
  package.yml                     # see below
  AGENTS.md                       # starter engine guide for AI agents, by engine kind (14_working_with_ai.md)
  config/routes.rb                # the module's own routes
  config/module.rb                # registry entry (ARCH-06)
  config/locales/<locale>.yml     # one per locale in config/locales.yml
  config/errors.yml               # module error codes, prefixed "billing."
  config/permissions.yml          # resources × actions (BE-03)
  config/budgets.yml              # page overrides, empty (TS-02)
  config/ratchets.yml             # this engine's ratchet counts (09_enforcement.md)
  config/contracts/               # generated JSON Schemas
  db/migrate/                     # the engine's migrations; tables prefixed billing_ (ARCH-10)
  app/public/acme/billing/        # Ruby public surface (ARCH-09)
  app/frontend/public/            # TS public surface, imported as @billing/public/...
  app/frontend/{pages,screens,containers,components,hooks,domain,forms}/
  app/frontend/components/skeleton.test.tsx   # one minimal test for the billing project (jsdom)
  app/frontend/domain/skeleton.test.ts        # one minimal test for the billing:node project
  spec/fixtures/upstream/         # per-upstream fixtures (TS-03)
  e2e/                            # browser tests (TS-04)
  tsconfig.json                   # generated by script/ci/engine_graph: composite project, references from package.yml
  vitest.config.mts               # Vitest projects billing (jsdom) and billing:node (TS-09); plugins from reactPlugins() (FE-10)
```

```yaml
# engines/billing/package.yml (generated)
enforce_dependencies: strict
enforce_privacy: strict
public_path: app/public/
dependencies:
  - engines/core
  - engines/design_system
```

- The registry entry in `config/module.rb` takes the next free navigation
  order in steps of 10 (10, 20, 30, …), so a later module can be placed
  between two others without renumbering. Mounting and navigation come from
  the registry (ARCH-06).
- `--icon <name>` sets the registry entry's `nav.icon`, a name the
  design_system icon map has (FE-17; the registry icon spec fails on any
  other). Without it the entry gets `folder`, a name the shipped icon map
  has.
- After writing the engine, the generator runs the post-write steps of
  GEN-09. Among them, `script/ci/engine_graph` writes every generated
  tsconfig file: the new engine's composite project, every engine's project
  references, `app/frontend/tsconfig.json` and `tsconfig.tooling.json`
  (which reference every engine), and the root solution file. It also
  regenerates the dependency-cruiser engine rules, all from every
  `package.yml` (ARCH-08). `npm run aliases:generate` writes the alias
  `paths` in `tsconfig.base.json` and `config/frontend_aliases.mts`
  (`engineAliases` with the `@engines` alias, and `engineFsAllow` for
  `server.fs.allow`, because Vite's root is `app/frontend`; FE-10). Generated
  frontend code imports only `@core/`, `@design_system/`, and its own
  `@<module>/` (ARCH-04).
- The engine's migrations stay in `engines/<module>/db/migrate`. The
  generated `engine.rb` appends that folder to the application's migration
  paths in an initializer, so `bin/rails db:migrate` runs them where they
  live and nothing is copied into the app. `Rafelo/EngineTablePrefix` reads the
  engine from the migration's file path (ARCH-10).
- The `Gemfile` loads engines by a glob over `engines/*/*.gemspec`
  (ARCH-11), so the generator does not edit it. `Gemfile.lock` still changes;
  the generator's `bundle install` step (GEN-09) updates it.
- Further dependencies (a domain engine, another module's public surface) are
  added to `dependencies:` by hand (ARCH-08). That is a guard-file change a
  person approves (`09_enforcement.md`).
- Vitest picks up the engine's two projects, `<module>` (jsdom: `*.test.tsx`
  and `hooks/**/*.test.ts`) and `<module>:node` (every other `*.test.ts`),
  through the root configuration's project list (TS-09); verify the project
  glob when adopting. Vitest exits 1 when a project has no test file, so the
  skeleton ships one minimal test per project and `bin/check` passes before
  the first page exists.

```ruby
# engines/billing/lib/acme/billing/engine.rb (generated, excerpt)
module Acme
  module Billing
    class Engine < ::Rails::Engine
      isolate_namespace Acme::Billing

      # Run this engine's migrations from engines/billing/db/migrate (verify when adopting).
      initializer "acme_billing.migration_paths" do |app|
        config.paths["db/migrate"].expanded.each { |path| app.config.paths["db/migrate"] << path }
      end
    end
  end
end
```

### GEN-02 — `rafelo:page` creates a complete, passing slice (MUST · ADR-06, ADR-13)

For `rafelo:page <module> <resource> [--actions=index,show,new,edit]` (default
`index`) the page generator creates, per action:

| Layer | Files |
| --- | --- |
| Rails | controller actions (BE-01 for reads, BE-13 for `create`/`update`), policy methods that require the module's permission constants (BE-03), a gateway stub that declares its upstream (BE-06), props objects (BE-04) that build every URL the page needs through `context.urls`, and a form object for `new`/`edit` |
| Permissions | the resource and its actions in the module's `config/permissions.yml`; the post-write steps (GEN-09) regenerate the Ruby constants and TypeScript |
| Frontend | `pages/<resource>/<action>.tsx` with `.schema.ts` built by `definePage` with the page's `can` keys (CT-01, CT-03), screen, container, components, and types files; links and form actions use the URLs in props, never URLs built in TypeScript; `new`/`edit` pages use `useForm` and add the form token and the edit version from the current props at submit time (BE-15); test ids follow FE-09 |
| Copy | titles, empty states, and field labels in the module's locale file for every configured locale |
| Contracts | the page's JSON Schema in `engines/<module>/config/contracts/`, written by the post-write steps (GEN-09) |
| Tests | request specs under the default locale prefix asserting schema and budgets at the maximum page size, with a fixture that supplies that many items, `have_resolvable_hrefs`, and `match_policy_capabilities` for the page's `can` keys (TS-02, TS-03, ARCH-10); redirect and error paths for writes; component tests |
| Routes | resourceful routes in the module's `config/routes.rb` |

When `config/upstreams.yml` names more than one upstream, `--upstream=<name>`
chooses the one the gateway declares.

- It refuses a resource whose singular equals its plural (`equipment`,
  `news`, `series`): Rails then names the collection route `<name>_index`, so
  every generated route name would shift.
- It refuses a resource the module already has, so one run creates one
  complete set of actions; actions are added to an existing resource by hand
  or by a later generator, never by overwriting files.
- The module's first `index` page also adds the engine's `root` route, which
  navigation links to (ARCH-06).

Entries for every locale other than the default are generated as visible
placeholders (`"[th] Invoices"` in the default configuration), so the parity
check passes but untranslated copy is obvious in review. A release fails while
any placeholder remains (CT-08, WF-05).

### GEN-03 — Templates read contracts instead of copying them (MUST · ADR-06)

Templates never hardcode what a contract or a configuration file already says:

- the namespace comes from `Rails.application.class.module_parent_name`
  (`Acme` in Rafelo);
- the locale list comes from `config/locales.yml`, and the URL prefix in
  generated specs from `I18n.default_locale`;
- the envelope comes from core helpers: page props build on
  `Acme::Core::PageProps`, which returns exactly the five page keys (core
  merges the shared keys, CT-01), and page schemas on `definePage`;
- permission keys come from the module's generated permission constants;
- TypeScript project references and dependency-cruiser rules come from the
  `package.yml` dependency lists.

When a contract or a configuration file changes, generated code changes with
it.

### GEN-04 — CI runs the generators end to end (MUST · ADR-04)

The smoke test creates a domain engine, two modules, and a read and a write
page, checks them, then moves the page and renames a module and checks again.
CI runs it on the triggers in TS-06: pull requests that touch generator
templates, core contract helpers, the registry code, or routing, and nightly.
It is a `bin/ci` step (`09_enforcement.md`) that CI runs as its own job,
whose `if:` declares the skip on every other pull request (WF-03).

```sh
#!/usr/bin/env bash
# script/ci/generator_smoke
set -euo pipefail
export BUNDLE_FROZEN=false # each new engine changes Gemfile.lock; other CI jobs, except the production image build (OPS-06), run with BUNDLE_FROZEN=true (WF-06)

# bin/ci runs this locally too: refuse to start on uncommitted or untracked work,
# because the cleanup below restores the whole tree.
if [ -n "$(git status --porcelain)" ]; then
  echo "generator_smoke: needs a clean working tree; commit or stash first" >&2
  git status --short >&2
  exit 1
fi

cleanup() {
  # The tree was clean at the start, so this removes only what the run created,
  # inside and outside engines/ (Gemfile.lock, generated aliases). Ignored files stay.
  git checkout -- . && git clean -fdq
  bundle install --quiet
}
trap cleanup EXIT # also after a failed step

verify() {
  # Each generator ran its own post-write steps (GEN-09); prove they left nothing stale.
  script/ci/engine_graph --check
  for check in aliases permissions errors i18n contracts; do npm run "${check}:check"; done
  for engine in "$@"; do bin/check "$engine"; done
  npm run pages:check
}

# Create: a domain engine, two product modules, a read page and a write page.
bin/rails generate rafelo:domain smoke_party
bin/rails generate rafelo:module smoke_check
bin/rails generate rafelo:module smoke_other
bin/rails generate rafelo:page smoke_check widgets --actions=index,new
verify smoke_party smoke_check smoke_other

# Change: move the resource to the other module, then rename that module.
bin/rails generate rafelo:move_page smoke_check smoke_other widgets
bin/rails generate rafelo:rename_module smoke_other smoke_renamed
verify smoke_check smoke_renamed
```

`bin/check <engine>` runs Packwerk, the generated dependency-cruiser rules,
`tsc -b`, both Vitest projects, RSpec, and ESLint for one engine
(`09_enforcement.md`). The
job fails if a generated module does not mount under the default locale
prefix, its props do not match its schema, its write path does not redirect
with errors, it breaks a dependency rule, it does not compile or lint, or a
moved or renamed page loses its old URL or permission prefix. This job and
the production image build, which runs `rafelo:module` before it builds
(OPS-06), are the only CI jobs that run with `BUNDLE_FROZEN=false`. It runs
in a disposable CI workspace, so the cleanup is a courtesy.

### GEN-05 — `rafelo:domain` creates a domain engine (MUST · ADR-03)

A domain engine holds a business concept that several modules share: its
gateway, value objects, and presentational components (step 2 of the
sharing ladder, ARCH-05). The generator creates the same skeleton as GEN-01
with these differences:

- no `config/routes.rb`, no `config/module.rb`, no pages, no navigation, no
  registry entry, no `config/budgets.yml`, and no `config/permissions.yml`
  (a domain engine has no permission prefix);
- `app/public/acme/<name>/` and `app/frontend/public/` are what consumers use;
  everything else is private (ARCH-09);
- its own i18n namespace for its presentational components;
- `package.yml` declares `engines/core` and `engines/design_system`, with
  strict dependency and privacy enforcement.

A consumer, a product module or another domain engine, declares the new
engine in its own `dependencies:`. The generator does not do that for it.

### GEN-06 — Modules can be renamed, split, and moved (MUST · ADR-04, ADR-29)

A module that outgrows its size budget (ARCH-12) is split; a module whose name
no longer fits is renamed. Both are generator work, not hand edits.

- `rafelo:rename_module <old> <new>` renames the engine folder, gemspec,
  namespace, TypeScript alias, i18n namespace, error-code prefix, and permission
  constants, and updates every `package.yml` that depends on it (a guard-file
  change a person approves).
- `rafelo:move_page <from> <to> <resource>` moves one resource's slice (Rails
  classes, frontend files, copy, contracts, permission entries, specs,
  fixtures, and browser tests) from one module to another. When the source's
  `root` route points to the moved resource, it re-points `root` to the first
  remaining `index` page in the source's `config/routes.rb`, or removes it
  when none is left (the source then leaves navigation, ARCH-06). When the
  target has no `root` route and the moved resource has an `index` page, it
  adds `root` there, as GEN-02 does.
- Splitting a module is `rafelo:module` for the new half, then `rafelo:move_page`
  for each resource that moves. Code both halves still need becomes a public
  interface or a domain engine (ARCH-05), never a copy.

Both generators run the post-write steps of GEN-09, so the TypeScript
projects, the dependency-cruiser engine rules, the engine aliases, and the
generated permissions, error codes, locale files, and contracts follow the
new names.

By default, URLs and permission keys stay stable, through the registry
(ARCH-06): a renamed module keeps its old `path:` and `permission_prefixes:`;
a moved resource's old URL prefix gets a `legacy_paths:` entry in the
target's registry entry that maps it to the resource's path there
(`{ "/billing/refunds" => "/refunds" }`, answered with a 301), and the target
module declares the source's permission prefix (boot validation allows a
shared prefix and refuses only a duplicate permission key, ARCH-06). Upstream
grants and bookmarks keep working. Both generators add request specs that pin
the old URL and the old permission keys.

Moved and renamed pages get new Inertia component names; open tabs reload on
the next visit through the asset version (CT-12). Two things cannot be
rewritten in the same release, and the generator handles both explicitly:

- Tables the engine owns keep their old prefix until a later migration that
  follows BE-22 renames them. The generator records
  `metadata: { legacy_table_prefix: <old> }` in the engine's `package.yml`;
  `Rafelo/EngineTablePrefix` accepts that prefix until the entry is removed.
- Jobs already enqueued under old class names keep working for one release
  through constant aliases the generator writes to
  `config/initializers/legacy_constants.rb`; the next release deletes them
  (ADR-31).

Both counts are ratcheted in the engine's own `config/ratchets.yml`
(`legacy_table_prefixes`, and `legacy_constants` for the aliases that point
into the engine): a count rises only with an owner's approval, and every
fall becomes the new ceiling.

### GEN-07 — Adoption by application template; tracked kernel updates (MUST · ADR-27, ADR-28)

A new project starts from the Rails application template:

```sh
# runs in a throwaway container, so nothing is installed on the host
docker run --rm -it --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD":/work -w /work ruby:<pinned> \
  sh -c 'gem install rails -v <pinned> && rails new <app> -d postgresql --devcontainer --skip-javascript --skip-hotwire --skip-jbuilder --skip-test -m <template>'
```

`<pinned>` is the Ruby image tag and the Rails version of the template
release. `--user` makes the generated files belong to you rather than root,
and `HOME=/tmp` gives that user a writable home. `-d postgresql` and
`--devcontainer` set up PostgreSQL and the Dev Container (OPS-09); the skip
flags leave out what the template replaces (the default JavaScript setup and
Hotwire by Vite, React, and Inertia; Jbuilder by props objects; Minitest by
RSpec). The template asserts these options and stops when one is missing.
Verify the Rails 8.1 flag set, and that the image has git, when adopting.

- The template derives the namespace from the app name (`acme` → `Acme`),
  copies in the kernel (`engines/core`, `engines/design_system`, the
  generators, `script/ci/`, `bin/check`, `bin/kernel_update`,
  `spec/fixtures/hostile_urls.json`), the guard
  configurations and canaries, the example engines (GEN-08), the
  documentation, and the AI files (`14_working_with_ai.md`), and writes
  `KERNEL_VERSION` with the template release it copied. Every file it copies
  is rendered with the app's name, documentation and `.github/` included, so
  no `acme` remains in any letter case (`Acme`, `acme_`, `acme/`,
  `@acme/`, `ACME_`).
- Before it writes anything, the template refuses an app name whose
  namespace collides with Rafelo's own: one whose camelized form is `Core`,
  `DesignSystem`, `Rafelo`, `Engines`, `App`, `ExampleOrders`, or
  `ExampleCustomers`, or one that is already a constant once the template's
  gems are loaded. Rails refuses only its reserved words and the constants
  loaded in the generator process (railties 8.1.4.1, `app_name.rb`), so it
  would accept all of these.
- It ends with an initial commit of everything it wrote: `rails new` runs
  `git init` but commits nothing (railties 8.1.4.1), and the first `bin/ci`
  needs a clean tree and a base commit (GEN-04 refuses a dirty tree). The
  throwaway container has no git configuration, so the commit names its own
  author, `Rafelo template <template@rafelo.invalid>`; it holds only what the
  template wrote.
- Kernel-owned names keep the Rafelo brand in every adopter and are never
  renamed: the generator namespace `rafelo:` and the RuboCop department
  `Rafelo/`. Only the app namespace (`Acme`) follows the app name.
- From then on the kernel belongs to the adopter, security included. Nothing
  updates it remotely.
- `bin/kernel_update <version>` produces a three-way merge for every kernel
  file it updates: the adopter's copy, the base release named in
  `KERNEL_VERSION`, and the new release, both releases rendered with the
  adopter's namespace first.
  It applies clean merges, leaves conflicts marked for a person to resolve,
  and updates `KERNEL_VERSION`. The result is an ordinary pull request that
  must pass `bin/ci`.
- By default it updates core, the generators, `script/ci/`, `bin/check`,
  `bin/kernel_update`, `spec/fixtures/hostile_urls.json` (FE-18), and the guard
  configurations. design_system is updated
  only folder by folder, on request
  (`bin/kernel_update <version> --include design_system/<folder>`), because
  adopters restyle it.
- The template's own CI adopts the commit under test: it packs `HEAD` with
  `git archive`, runs `rails new` with the application template from that
  archive under a two-word app name that is not `acme` (for example
  `smoke_shop`, so the camel-case and underscore forms are both exercised),
  then `bin/setup --skip-server` and `bin/ci` in the new app, and fails when
  any tracked path or file of the new app still contains `acme` in any letter
  case. It also adopts release N-1, updates it to N with `bin/kernel_update`,
  and runs `bin/ci`, so every release is reachable from the one before.
  Template specs refuse each reserved app name above.
- The template repository has a `SECURITY.md` for reporting vulnerabilities
  in the template. Fixes reach adopters through `bin/kernel_update`.

### GEN-08 — The example engines are examples (MUST · ADR-27, ADR-32)

The template ships two complete engines to learn from, for people and for AI
(`14_working_with_ai.md`):

| Engine | Kind | Shows |
| --- | --- | --- |
| `engines/example_orders` | product module | a list with filters and pagination, a show page, new and edit with the form token and a conflict, a deferred chart, an export job |
| `engines/example_customers` | domain engine | a gateway, value objects, a public presentational component |

- They are deep and complete: every layer, every test level, every guard
  green. Each has a README saying it is an example to learn from, not a
  feature to keep.
- Nothing outside `example_*` may depend on them, in Ruby or TypeScript. A
  canary proves the check fires (TS-07).
- No kernel spec depends on them: the kernel's own request specs run against
  the test-only `engines/core/spec/dummy_engine`, which loads only in the test
  environment, belongs to core's Packwerk package, and is left out of the page
  resolver and `pages:check` (TS-01). The example engines
  show the kernel in use and may exercise the same behaviour.
- The template's CI deletes both engines and runs `bin/ci`, so they are
  provably removable and deleting them removes no proof.
  `bin/kernel_update` never touches them.
- Delete them once your own first module can serve as the reference.

### GEN-09 — Generators are all or nothing (MUST · ADR-04)

A generator that fails halfway leaves a half-wired engine that the next run
refuses as already taken. Every generator therefore validates its inputs and
renders every file in memory before its first write. It then writes them and
runs the same post-write steps, in this order:

1. `bundle install`;
2. `script/ci/engine_graph`;
3. `npm run aliases:generate`;
4. `npm run permissions:generate`;
5. `npm run errors:generate`;
6. `npm run i18n:generate` (the locale export);
7. `npm run contracts:generate`;
8. the formatter, `prettier --write` on the files it wrote.

A step with nothing to change leaves the tree as it is. If any step fails, the
generator restores every file it created or changed, removes what it added,
and names the failed step. A generator spec injects a failure into each step
and asserts a clean `git status` afterwards.
