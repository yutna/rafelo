# 07 — Testing

Test each behaviour once, at the cheapest level that proves it. Contracts and
budgets are tested on every page, so regressions in shape, query count, and
payload size fail fast. Tests live in the engine they test, next to the code
they prove, so a module's suite moves with the module.

## Rules

### TS-01 — Choose the cheapest useful level (MUST · ADR-20)

| Behaviour | Level | Tooling |
| --- | --- | --- |
| A page or endpoint (status, component name, props, redirects, errors) | request spec — the main Rails integration test | RSpec |
| A policy, props object, gateway mapping, value object, middleware | plain Ruby spec | RSpec |
| A domain class or form model, including its round trip (OOP-10) | unit test, no DOM | Vitest (`<engine>:node` project, TS-09) |
| A hook | `renderHook` | Vitest (`<engine>` project, jsdom) + React Testing Library |
| A component or screen state (loading, empty, error, forbidden) | render test | Vitest (`<engine>` project, jsdom) + React Testing Library |
| A stored format written by the previous release (job arguments, idempotency outcomes, session rows) | compatibility spec over the previous tag's `spec/fixtures/formats/v<VERSION>/` (SEC-16) | RSpec |
| A race between requests (single-flight refresh, idempotency claim) | concurrency spec in its own lane (TS-10) | RSpec |
| How a design_system component looks | screenshot of the component catalog (TS-11) | Playwright |
| A critical journey across pages (sign-in, refresh, sign-out, one flow per module) | browser test | Playwright |

Use FactoryBot for BFF-owned records. Do not mock collaborators that are cheap
to use for real. At every level, a test that finds an element selects it as
TS-04 says.

The kernel proves its own behaviour. The write flow, the error responder,
translated errors, and the envelope are covered by request specs in core that
run against a committed test-only engine, `engines/core/spec/dummy_engine`,
which is never mounted outside tests:

- `config/application.rb` requires its engine file (under
  `engines/core/spec/dummy_engine/lib/`) only when `Rails.env.test?`, so its
  registry entry registers only then.
- It is part of core's Packwerk package and has no `package.yml` of its own.
- `contracts:generate` includes `engines/core/spec/dummy_engine/app/frontend`
  and writes its schemas to `engines/core/spec/dummy_engine/config/contracts/`;
  the tsconfig that `script/ci/engine_graph` writes for core includes the same
  folder, so `tsc -b` checks it.
- The page resolver's glob and `pages:check` leave out `engines/core/spec/`.

The example engines may exercise the same behaviour, but no kernel spec
depends on them, so deleting them (GEN-08) removes no proof.

The format fixtures under `spec/fixtures/formats/` are generated by
`bin/rails formats:dump` and committed in the release pull request that bumps
`VERSION` (WF-05, SEC-16), never written by hand.

The test environment uses a real in-memory cache:
`config/environments/test.rb` sets `config.cache_store = :memory_store`,
because `rate_limit` takes its store when the controller class loads, and a
global `before` hook clears the cache before every example. Throttle specs
(BE-12) therefore count for real, and no example sees another's entries.

### TS-02 — Every page proves its contract and budgets (MUST · ADR-06, ADR-20)

Each Inertia page has a request spec that asserts:

- the component name and status;
- the props match the generated JSON Schema, which is strict, so a prop
  outside the schema fails (CT-03, CT-10). `match_page_schema` maps the page
  key to a file under the owning engine's `config/contracts/` and raises on an
  empty, `.`, or `..` segment, so a key cannot leave that folder; its failure
  message lists each failing JSON pointer with its error (json_schemer's
  `data_pointer`), never the whole props;
- the number of SQL queries and the number of upstream calls per named
  upstream made inside the `within_budgets` block are within budget (BE-16;
  session and grant refreshes, and the resend after a refresh, are counted
  separately). The block holds the
  request alone: factories, sign-in, and fixture setup stay outside it and are
  not counted, and the matcher raises when it is called without a block. SQL
  queries are counted as OPS-01 defines them (no `SCHEMA` or `TRANSACTION`
  event, no query-cache hit), by the subscriber the request log uses. Active
  Record 8.1.4.1 marks a cache hit with `payload[:cached]` and keeps the
  query's own name, so a filter on the name `CACHE` would count it;
- the serialized props are within the page's byte budget, measured at the
  maximum page size;
- every URL in the props was built by Rails
  (`expect(inertia_props).to have_resolvable_hrefs`, a core matcher).
  `Acme::Core::Urls` records every path it builds for the request
  (`urls.built`, cleared per request), and the matcher asserts that the path
  part, without the query string, of every app-relative `href`, `*Href`, and
  `nav[].path` is in that set. A route helper raises on an unknown route
  name, so a recorded path resolves. Core's own specs prove the matcher, and a
  canary proves it fires (TS-07; CT-02, ARCH-10);
- every capability agrees with its policy
  (`expect(page).to match_policy_capabilities`, a core matcher): over a grant
  matrix (no grant, the exact key, the resource and prefix wildcards, the
  guarding flag off), `can[key].allowed` equals the answer of the policy
  method the capability names (BE-04).

Shared props are not part of the page's budget; they have their own, measured
once in their own spec (CT-13).

The props budget is measured on the largest page a viewer can request. For a
list page, `be_within_props_budget` fails unless `pagination.perPage` equals
the `ListQuery` maximum (BE-07) and the list holds that many items, so the spec
needs a fixture that supplies them. A page declared with `paginated: false`
(`definePage`, CT-03), whose generated schema allows only `null` for
`pagination`, has no list to page through and is exempt from that rule.

Each of these matchers records the page key it checked (a matcher without a
page argument records the component of the spec's last Inertia response) in
`tmp/page_matchers/<process>.json`, one file per `parallel_tests` process;
`bin/ci` empties the folder before RSpec runs. After the RSpec run,
`pages:check --matchers` reads those files and fails when a page of an engine
the run covered, or of the app, has no recorded call of `match_page_schema`,
`within_budgets`, `be_within_props_budget`, `have_resolvable_hrefs`, and,
when it declares `can` keys, `match_policy_capabilities`. It never searches
spec text: a matcher named in a comment, or in a spec that does not run,
records nothing.

Budgets come from two places. The root file holds the defaults every page
inherits, the growth budgets (ARCH-12), and the connection budget (BE-21); a
spec asserts it has no `pages:` key. Each engine holds the overrides for its
own pages (ARCH-11). The matchers merge the two; the bundle check reads the
root defaults.

```yaml
# config/budgets.yml  (defaults, growth, and connection budgets only; the values are examples)
defaults:
  sql_queries_per_request: 12
  upstream_calls_per_request:      # per named upstream in config/upstreams.yml
    api: 3
  props_bytes: 65536               # at the maximum page size
  shared_props_bytes: 8192         # CT-13
  js_entry_gzip_kb: 250
  js_page_chunk_gzip_kb: 60        # page chunk plus its static imports the entry does not load (FE-16)
  js_lazy_chunk_gzip_kb: 120       # each lazily imported chunk (FE-16)
  js_initial_gzip_kb: 300          # smallest page: entry plus its shared imports (FE-16)
  boot_seconds: 8                  # TS-09
growth:                            # ARCH-12; raising any value needs an ADR
  core: { max_files: 400, max_public_exports: 120, max_public_constants: 80 } # set at adoption
  design_system: { max_public_exports: 150 }                                  # set at adoption
  domain_engine: { max_public_exports: 40, max_public_constants: 20 }         # public surface size; set at adoption
  module: { max_files: 600, max_pages: 40 }                                   # set at adoption
  fan_in: { max_dependents: 5 }      # dependents of a product module; core and design_system are not counted
  touch_rate: { max: 0.15, min_modules: 3 }                                   # over 30 days; job runs from 3 product modules, examples not counted
connections: { server_max_connections: 100, budget: 90, headroom: 10 }        # BE-21; root level, not under growth:
```

```yaml
# engines/billing/config/budgets.yml  (overrides for this engine's own pages only)
pages:
  billing/invoices/index:
    props_bytes: 98304
```

An override names one of the engine's own pages and states its reason in the
pull request that adds it. The number of overrides is ratcheted in the
engine's own `config/ratchets.yml` (ARCH-11), so adding one raises a count,
and a raise needs a person to approve it.

```ruby
# engines/billing/spec/requests/invoices_index_spec.rb
RSpec.describe "Billing invoices index", type: :request do
  let(:max) { Acme::Core::ListQuery::MAX_PER_PAGE }

  it "renders within its contract and budgets at the maximum page size" do
    sign_in_as viewer_with(Acme::Billing::Permissions::INVOICE_READ)
    stub_upstream_list(:api, :invoices, count: max) # fixture from spec/fixtures/upstream/api/

    within_budgets("billing/invoices/index") do      # counts SQL queries and upstream calls inside this block only
      inertia_get "/#{I18n.default_locale}/billing/invoices", params: { per_page: max } # sends X-Inertia-Version (CT-12)
    end

    expect(response).to have_http_status(:ok)
    expect(inertia_component).to eq("billing/invoices/index")
    expect(inertia_props).to match_page_schema("billing/invoices/index")
    expect(inertia_props).to be_within_props_budget("billing/invoices/index") # requires perPage == max
    expect(inertia_props).to have_resolvable_hrefs # every href, *Href, and nav[].path was built by Urls (CT-02)
    expect("billing/invoices/index").to match_policy_capabilities # each can[key].allowed equals its policy method (BE-04)
  end
end
```

Prosopite raises on N+1 queries in the test environment: `spec/rails_helper.rb`
sets `Prosopite.raise = true` and wraps every example in a scan
(`Prosopite.scan` before it, `Prosopite.finish` after it). An example turns
the scan off only with the metadata `prosopite: false`. Under
`spec/enforcement/` that needs nothing more: the N+1 canary scans its own
block there. Anywhere else the metadata, and `Prosopite.pause`, are skip forms
(TS-05): each needs a linked issue on the same line and counts in the skip
ratchet.

### TS-03 — Fake each upstream, check it for drift (MUST · ADR-01, ADR-20, ADR-30)

- Tests never reach the network. Each named upstream in `config/upstreams.yml`
  has one small Rack app in core that serves recorded responses for it.
- Fixtures live in the engine that uses them:
  `engines/<engine>/spec/fixtures/upstream/<upstream>/`. The fake app composes
  them by scanning every engine at load, so adding a module never edits the
  fake. A check asserts the central fake app holds no module paths.
- In RSpec, WebMock routes each upstream host to its fake app in-process.
- Playwright drives a real server process, where WebMock does not apply. There
  each fake app is mounted at a development-only path (SEC-12) and that
  upstream's base URL points at it.
- That server runs in the `test` environment, started by Playwright with
  `E2E_SERVER=1`. `config/environments/test.rb` sets
  `config.action_controller.allow_forgery_protection = true` when
  `E2E_SERVER` is set, so the browser tests prove the real CSRF token path;
  RSpec never sets it and keeps the test default, `false` (SEC-05). The smoke
  job also sets `csp.report_only` to `true` and fails when
  `/core/csp_reports` received a report during the run (SEC-05).
- The fixtures are the consumer contract: each one is a real, anonymized
  response shape with only synthetic values.
- Drift is checked per upstream. A scheduled, non-blocking job calls each
  upstream's staging environment with a test account and compares response
  shapes with every engine's fixtures for that upstream. When the upstream
  publishes a grant catalog, the same job diffs the permission manifests
  against it (BE-03). A mismatch opens an issue naming the upstream and the
  engines whose fixtures differ; it does not block merges.
- Browser tests live per engine in `engines/<engine>/e2e/`; the app's own
  journeys (sign-in, refresh, sign-out) live in the root `e2e/`.

### TS-04 — Tests select by role and name, or by test id (MUST · ADR-20)

Playwright and React Testing Library select an element in one of two ways:

- by role with its accessible name, where the name comes from an i18n key
  through a test helper that resolves the key in the test's locale, so a copy
  change or a locale switch does not break the test;
- by test id (FE-09), for states and for elements without a useful role.

Never by CSS selector, tag name, or literal visible text. Text queries count
as literal text in every variant: Testing Library's `getBy`, `queryBy`,
`findBy` and their `All` forms over `Text`, `LabelText`, `PlaceholderText`,
`DisplayValue`, `Title`, and `AltText`, and Playwright's `getByText`,
`getByLabel`, `getByPlaceholder`, `getByAltText`, and `getByTitle`. FE-09 test
ids stay required on every interactive design_system component and every
loading, empty, error, and forbidden state.

```ts
// engines/billing/e2e/invoices.spec.ts (excerpt)
// i18nName: core test helper that resolves an i18n key in the test's locale
await page.getByRole("button", { name: i18nName("billing.invoices.export") }).click();
await expect(page.getByTestId("billing.invoices.empty")).toBeVisible();
```

Playwright has one project per engine, generated by scanning for `e2e/`
folders, plus the root project for the app. Each pull request runs a small
Chromium smoke suite for the affected engines' projects and the app; the full
Chromium, Firefox, and WebKit suite runs nightly. The `design_system` project
holds the catalog screenshots (TS-11) and runs in Chromium only, the one
browser with baselines.

```ts
// playwright.config.ts (excerpt)
import { existsSync, readdirSync } from "node:fs";

import { defineConfig } from "@playwright/test";

const suites = [
  { name: "app", testDir: "e2e" },
  ...readdirSync("engines")
    .filter((engine) => existsSync(`engines/${engine}/e2e`))
    .map((engine) => ({ name: engine, testDir: `engines/${engine}/e2e` })),
];
// as const: `use.browserName` takes only Playwright's browser names, never a plain string
const browsers = process.env.E2E_ALL_BROWSERS ? (["chromium", "firefox", "webkit"] as const) : (["chromium"] as const);

export default defineConfig({
  use: { testIdAttribute: "data-testid" },
  projects: browsers.flatMap((browserName) =>
    suites
      // design_system's suite is the catalog screenshots (TS-11): Chromium baselines only
      .filter((suite) => suite.name !== "design_system" || browserName === "chromium")
      .map((suite) => ({ ...suite, name: `${suite.name}:${browserName}`, use: { browserName } })),
  ),
});
```

### TS-05 — No duplicate or skipped assertions (MUST · ADR-20)

- Do not assert the same behaviour at several levels. When a contract test
  proves it, do not add a browser test for it.
- Cover the valid case, the invalid case, and the edge that would break the
  rule.
- A guard spec proves its guard. Its input reaches the guarded path, it
  asserts the guarded outcome (the response, the value refused, what was or
  was not read, written, or sent), and its description says what it asserts.
  A spec that would still pass with the guard removed does not count. A limit
  on a stream is crossed after the first chunk, by a fake that delivers the
  body in chunks, and the spec asserts that nothing past the limit was read or
  written (SEC-14).
- A parser of untrusted input has a table spec with one row per refused class
  and its outcome: the return-to path (SEC-11), list parameters (BE-07),
  `traceparent` (OPS-02), upstream path segments (SEC-14), and the client
  error report (OPS-03). Parameter parsers are fed real
  `ActionController::Parameters`, with arrays and hashes where a scalar is
  expected.
- An absence assertion (a token, a viewer id, or personal data must not
  appear) checks each forbidden value on its own against the whole captured
  output: every log line, every metric with its tags, the whole body. A
  pattern that needs two values on one line misses the line that leaks one.
  Log and metric specs parse every JSON line and compare its keys, metric
  tags included, with the OPS-01 allow-list, so a new key fails.
- Every way of skipping a test requires a linked issue in the same line:
  - RSpec: `skip`, `pending`, `xit`, `xspecify`, `xexample`, `xdescribe`,
    `xcontext`, and the metadata `:skip`, `skip:`, and `pending:`; outside
    `spec/enforcement/`, also the metadata `prosopite: false` and
    `Prosopite.pause` (TS-02);
  - Vitest: `it.skip`, `test.skip`, `describe.skip`, `it.todo`, `test.todo`,
    and the conditional `it.skipIf`, `test.skipIf`, `describe.skipIf`;
  - Playwright: `test.skip` (as a modifier inside a test too),
    `test.describe.skip`, `test.fixme`, and `test.describe.fixme`.

  A linked issue is `#<number>` with no space after `#` (`# see #123`), or a
  full issue URL; `# 5 seconds` does not count. The number of skips is
  ratcheted: a count rises only with an owner's approval, and every fall
  becomes the new ceiling.

### TS-06 — Generators are tested by running them (MUST · ADR-04, ADR-20)

Generator specs that only compare file text miss real breakage. CI runs the
generator smoke test described in GEN-04:

- on pull requests that touch the generator templates
  (`engines/core/lib/generators/`), the core contract helpers (`definePage`,
  the envelope, `Acme::Core::PageProps`), the module registry code, or
  routing;
- nightly on `main`, so a change outside those paths that breaks generation is
  caught within a day.

The smoke test is slow (it installs gems and type-checks the whole app), which
is why it does not run on every pull request.

### TS-07 — Every custom enforcement rule proves it fires (MUST · ADR-20, ADR-32)

A lint or architecture rule with a wrong path pattern passes forever while
checking nothing. Each custom rule has a canary fixture under
`spec/enforcement/fixtures/` that deliberately breaks it. A CI step
(`script/ci/enforcement_canaries`) runs the tool on each fixture and fails
unless every expected rule reports its error. Fixtures are excluded from the
normal runs. Canary fixtures are guard files: changing one needs a person's
approval (`09_enforcement.md`).

A canary runs the tool with the repository's own configuration file
(`eslint.config.mjs`, `.rubocop.yml`, `.dependency-cruiser.cjs`,
`packwerk.yml`), unchanged. It never carries a copy of a rule: a copied rule
proves only the copy. The one thing a canary lifts is the fixtures exclusion,
and it does so by putting the fixture at a real path, never by editing the
configuration.

A canary passes only when both hold:

- the tool exits with its findings status: ESLint and RuboCop exit 1 (their
  exit 2 is a crash or a configuration error, never a pass), Packwerk exits 1,
  and dependency-cruiser and every `script/ci/` check exit non-zero;
- its machine-readable output names the expected rule for the fixture's file:
  `ruleId` in ESLint's `--format json`, `cop_name` in RuboCop's
  `--format json`, the rule name in dependency-cruiser's `--output-type json`,
  the violation type in Packwerk's output, the rule ID in a check's message.

An exit status alone proves nothing. ESLint 9.39.5 exits 1 on a parse error
with `ruleId: null`, and exits 0 with only a warning for a file at an ignored
path or outside every `files:` glob; RuboCop 1.92.2 exits 1 on a fixture
outside a cop's `Include` because another cop fired; Packwerk 3.3.1 `check`
exits 0 when every file is excluded ("No files found or given"). So a crash, a
configuration error, a parse error, an ignored file, and a run that inspected
no file all fail the canary.

A fixture proves that a rule's selector fires, not that the real
configuration applies it where the code lives. A path-scoped rule (an ESLint
`files:` block, a cop's `Include`, a dependency-cruiser path) can match
nothing at real paths, and in a flat config a later block that sets the same
rule for a folder replaces it there. Canaries therefore run at real paths:

- ESLint fixtures are linted with `--stdin-filename` set to a real path in
  each folder the rule targets (an engine page, a domain file, a unit test, an
  engine `e2e/` spec), so the real `files:` globs and overrides apply (verify
  the type-aware rules with stdin input when adopting). RuboCop fixtures are
  read with `--stdin` under a real file name the same way.
- For each ESLint restriction, `eslint --print-config` on one real file per
  scoped folder asserts that the resolved rule still holds every expected
  selector, property, or import entry.
- Dependency-cruiser and Packwerk canaries write their files at real engine
  paths for the run (uniquely named throwaway engines under `engines/`, with
  their own `package.yml` files for Packwerk) and remove them in an `EXIT`
  trap. No `package.yml` is committed under the fixtures folder: Packwerk
  3.3.1 finds packages by globbing every `package.yml` without applying
  `packwerk.yml`'s `exclude`, so the file would join the real graph.
- Every graph canary has a legal counterpart that must not be reported: a
  declared dependency used through its public surface, an `import type` of a
  declared engine, an acyclic declared pair. A rule that reports everything
  fails too.

Every `script/ci/` check, and every generator or check script behind
`npm run` (`contracts:*`, `errors:*`, `permissions:*`, `locales:*`, `i18n:*`,
`pages:check`, `aliases:*`, `docs:*`, `bundle:check`), can run on a fixture
tree:

- it takes `--root DIR` (default: the repository root) and reads and writes
  only under it;
- it prints how many inputs it checked (files, routes, rules, pages, entries)
  and fails when that number is zero;
- it fails when a command it runs (`git ls-files`, `bin/rails`, a tool)
  cannot start or exits non-zero;
- a check that reads a live system takes recorded input instead, so its
  canaries run without the network or a boot: `script/ci/repo_rules
  --payload FILE` (the rulesets API response), `script/ci/production_routes
  --routes FILE` (a recorded route walk), and `script/ci/guard_approval
  --reviews FILE` and `script/ci/ratchet --reviews FILE` (the pull request's
  reviews, for the approval each reads from the GitHub API).

### TS-08 — Accessibility is checked automatically (MUST · ADR-24)

The Playwright smoke suite runs axe (`@axe-core/playwright`) on every page it
visits, with the WCAG 2.2 A and AA rule tags. Any serious or critical
violation fails the run. The same suite checks the page-change announcement
and focus move from FE-13 on one representative navigation.

### TS-09 — The suite runs in parallel within time budgets (MUST · ADR-20, ADR-29)

- Running one engine's specs still boots the whole app, so boot time is the
  floor of every Ruby test run and grows with every engine. CI times
  `bin/rails runner nil` in the test environment, with bootsnap on, and fails
  when it exceeds `boot_seconds` in `config/budgets.yml`.
- RSpec runs with `parallel_tests`. Each process has its own PostgreSQL
  database, named with `TEST_ENV_NUMBER`.
- CI runs the specs of the affected engines (`script/ci/affected`). CI caches
  `tmp/tsc/`, where each engine's TypeScript declaration output and
  `.tsbuildinfo` live.
- Vitest runs two projects per engine, and the root configuration adds the
  same pair for the app (`app` and `app:node`): `<engine>`, in jsdom, for
  `*.test.tsx` and `hooks/**/*.test.ts` (components, screens, hooks), and
  `<engine>:node`, in Node, for every other `*.test.ts` (domain classes, form
  models, chart option builders, the formatters). A test that renders outside
  `hooks/`, such as core's state wrapper tests, is a `*.test.tsx`. Domain
  tests that run without a DOM stay fast and cannot come to depend on one
  (OOP-10).
- Every CI job that runs steps declares `timeout-minutes`, so a hung job
  fails instead of holding the queue. The `ci.yml` jobs run in the prebuilt
  Dev Container image, referenced by digest (OPS-09), except the first job,
  which reads the digest, and the production image build, which needs Docker
  on the runner (the Dev Container image build is a workflow of its own); the
  `pull_request.yml` jobs and the release job run on `ubuntu-latest`.
- Locally, `bin/check <engine>` runs the same checks for one engine, both of
  its Vitest projects included; `bin/ci` stays the gate (`09_enforcement.md`).

```yaml
# config/database.yml (excerpt)
test:
  <<: *default
  database: acme_test<%= ENV["TEST_ENV_NUMBER"] %>
```

```yaml
# .github/workflows/ci.yml (excerpt)
jobs:
  rspec:
    needs: image # the first job reads .devcontainer/image_digest (WF-03)
    timeout-minutes: 20
    container: ${{ needs.image.outputs.ref }} # the prebuilt Dev Container image, by digest (OPS-09)
```

### TS-10 — Concurrency specs run in their own lane (MUST · ADR-20)

Specs that prove behaviour under concurrent requests (the single-flight
refresh and its losers in SEC-03, the idempotency claim, takeover fence, and
`unknown` outcome in BE-15, the grants-stale mark in SEC-15, the bounded
executor in BE-16) are tagged `:concurrency`.

- They do not run inside the transactional test wrapper, because each thread
  needs its own connection and must see the others' commits. They clean up by
  truncating the tables they wrote.
- They run serially, in their own CI lane, never inside the parallel run
  (`--tag ~concurrency` there, `--tag concurrency` in the lane).
- They are never retried. A concurrency spec that fails now and then has found
  a race, in the code or in the spec, and gets an issue.
- Each one forces the race it proves. The threads wait at a barrier
  (`Concurrent::CyclicBarrier`) and start together, and the first is held
  inside the critical section (a stub on the guarded step waits on a
  `Concurrent::CountDownLatch`) until the others have reached the guard, so
  the spec fails when the lock, claim, or fence is removed. Threads that may
  simply run one after another prove nothing.

### TS-11 — The design system has visual regression tests (MUST · ADR-11, ADR-20)

A design_system change reaches every module at once, and most visual
breakage passes every functional test.

- The component catalog is an app page, `component_catalog/index` (FE-01),
  drawn only in development and test (SEC-12), with a schema like any page:
  design_system cannot hold a page, because a page schema uses core's
  `definePage` and design_system imports nothing from core. It renders every
  public design_system component in each variant and state, in every
  configured locale. Its screenshot tests live in `engines/design_system/e2e/`,
  so they run in the `design_system` Playwright project, in Chromium only
  (TS-04).
- Playwright takes screenshots of the catalog and compares them with committed
  baselines. Animations are turned off and the screenshots are taken in the
  prebuilt Dev Container image (OPS-09), locally and in CI, so fonts and
  rendering are the same on every machine.
- The test runs on every pull request that changes `engines/design_system`,
  including one whose committed API file (`engines/design_system/api.d.ts`,
  FE-21) is unchanged, when the modules' RSpec and Playwright suites are
  skipped.
- A changed screenshot fails until the new baseline is committed in the same
  pull request, where a person reviews the old and new images.
- axe (TS-08) runs on the catalog page too, and its `color-contrast` rule
  (impact serious, tag `wcag2aa`) is the only contrast check: no test keeps
  its own table of colors or contrast pairs, which drifts from the tokens.
  axe-core 4.14.0 parses the `oklch()` values of Tailwind v4's palette
  (`oklch(0.205 0 0)` reads as `#171717`). axe records contrast it cannot
  compute (a gradient, an image, or an overlapping element behind text) as
  incomplete, not as a violation, so the catalog draws each component on a
  plain token background.
